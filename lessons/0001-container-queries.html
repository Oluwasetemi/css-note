1

Spot the question you are really asking

Responsive design has two different signals. Choosing the signal first makes the CSS straightforward.

Media query: global

Question: What is true about the viewport or device?

Use it for page navigation, the overall shell, motion preferences, print, or color scheme.

Container query: local

Question: How much room did this component receive?

Use it for cards, sidebars, widgets, reusable panels, and components placed in unpredictable slots.

The practical point A component can be narrow on a wide screen or wide on a smaller screen. Viewport width is only an indirect guess; container width is the fact the component needs.

This is the starting point in Comeau’s friendly introduction: a profile card should switch layouts according to its own available space, not according to the browser window.

2

Learn the two-part grammar

First establish a measuring context. Then let a descendant react to it.

CSS · the minimum useful pattern 
/* 1. The ancestor becomes measurable */
.card-slot {
  container-type: inline-size;
}

/* 2. Base style: works in a narrow slot */
.profile-card {
  display: grid;
  gap: 1rem;
}

/* 3. Enhancement: room now exists for columns */
@container (min-width: 30rem) {
  .profile-card {
    grid-template-columns: auto 1fr auto;
    align-items: center;
  }
}
  1. Choose the boundary. Put container-type on the ancestor whose allocated space matters.
  2. Write the compact default. The component should work before the condition matches.
  3. Add the spacious layout. The @container block styles descendants when the boundary is wide enough.
Common mistake The query does not style the queried container itself. It applies styles to elements inside that container. A wrapper often makes this relationship explicit.

MDN specifies that size queries measure the container’s content box. See the @container reference.

3

Understand why containment exists

Without containment, a child could change the parent’s size, reverse the query, and create an endless layout loop.

Container is below the threshold
→
Query enlarges the child
→
Child enlarges the container; condition reverses

Comeau demonstrates this with a content-sized parent and a larger font inside the query. The conditional style changes the very measurement that activated it. The browser would bounce between true and false.

The rule to remember You cannot let queried content determine the dimension you are measuring.

Size containment breaks that feedback path. The container’s measured axis must get its size from layout context—such as stretching within its parent—or from an explicit size, rather than from the queried descendants. This is the foundation that made container size queries possible.

Source: MDN’s container-type description explains that size containment prevents child-size/query feedback loops.

4

Contain only the axis you need

Most components need to react to available inline space while their height continues to grow with content.

inline-size

Enables queries on the inline axis—usually width in horizontal writing modes.

The block axis can still grow around the content. This is the usual choice.

size

Applies containment in both inline and block axes.

If no contextual or explicit height exists, the box can collapse in that axis because its children no longer size it.

Safe default Start with container-type: inline-size. Reach for size only when you intentionally need both dimensions and have designed how the container gets both sizes.

In logical-property terms, inline size is not always physical width. In vertical writing modes it maps to the vertical dimension. The article says “typically width”; that word matters.

5

Apply the pattern that removes magic numbers

Let media queries arrange the page. Let container queries arrange the component inside its assigned region.

In Container Queries Unleashed, an email page has a metadata column. On a desktop it is one narrow column beside the message. When the page collapses to one column, that metadata region becomes wider—even though the viewport became narrower.

Viewport workaround

35rem–42rem OR 60rem+

Several breakpoints happen to predict the column width. A padding or gap change can invalidate them.

Container decision

metadata width ≥ 19rem

One threshold states the real design intent: this layout becomes comfortable at this component width.

CSS · shell outside, component inside 
/* Page-level decision */
@media (min-width: 60rem) {
  .email-layout {
    grid-template-columns: 19rem 1fr;
  }
}

.metadata-column {
  container-type: inline-size;
}

/* Component-level decision */
@container (min-width: 19rem) {
  .metadata-row {
    grid-template-columns: 7rem 1fr;
  }
}
Why this is useful The component now survives a sidebar, a dashboard grid, a full-width mobile row, and future shell changes without recalculating viewport breakpoints. Its CSS describes its own requirement.
6

Name a container when ancestry is ambiguous

An unnamed query uses the nearest eligible ancestor. A name lets you deliberately reach a different container.

CSS · select the intended measuring context 
.dashboard {
  /* shorthand: name / type */
  container: dashboard / inline-size;
}

.widget-slot {
  container: widget / inline-size;
}

/* React to the outer dashboard, not the nearer slot */
@container dashboard (min-width: 70rem) {
  .widget-tools {
    display: flex;
  }
}

Use names when multiple ancestors are query containers or when the queried relationship is not obvious. Otherwise, the nearest-container default keeps the code simpler. The shorthand is equivalent to setting container-name and container-type separately.

7

Choose the right signal

Retrieve the decision from memory. Immediate feedback will tell you whether your model is holding.

The primary navigation collapses into a menu when the browser becomes narrow. What should trigger it?

A reusable analytics widget moves between one-column and three-column dashboard slots. What should trigger it?

Your application checklist

  1. Identify a component currently using viewport breakpoints to guess its own width.
  2. Wrap it—or choose an existing boundary—that receives the relevant layout space.
  3. Add container-type: inline-size to that boundary.
  4. Keep the narrow component style as the default.
  5. Add one threshold where the alternative layout becomes comfortable, not where a device category begins.
  6. Test the component in at least two different parent layouts at the same viewport width.
One-sentence summary Use media queries for the environment; use container queries for the component’s allocated space.
